# Tests

Node test suites for the plugins in this repo. They exist because the plugins do
things that are painful to verify by clicking around a live Stash: fetch
interception, re-entrancy guards, error paths that need a failing server, and DOM
placement that depends on which of two identically-classed containers is mounted.

## Running them

```
node tests/run.js        # or: npm test
```

`run.js` runs the suites **in parallel**, bounded by the CPU count. Each is its own process
already — the plugins install global state, so they must not share a realm — and separate
processes are exactly what parallelises safely. Output is buffered per suite and released in
suite order, so a parallel run reads exactly like a sequential one; the whole tree went from
about 164 s to roughly its longest suite. To bisect a failure, run the one suite directly:

```
node tests/<suite>.test.js
```

No install is needed for most of it. Two suites skip themselves with a `SKIP` line unless
their dependency is present: `placement` needs a real DOM (`jsdom`), and
`scenevariants-render` needs **React 17** (`react`, `react-dom`) — pinned to 17 because that is
what Stash's own UI is on, and the thing that suite exists to catch is a difference between what
React does and what a hand-rolled stand-in was assumed to do.

```
npm install              # optional, enables the placement and scenevariants-render suites
```

Everything else is plain Node with no dependencies.

### No suite sleeps through real time

`placement.test.js` is the only one that cannot drive its ticks through a harness — it needs
jsdom's real layout to tell two identically-classed containers apart — so it used to wait on the
plugin's own `setInterval(tick, 1000)` in real seconds, 32 times, and cost 55 s of the tree's 164 s
on its own. It now runs the plugin's clock fast instead: `win.setTimeout` and `win.setInterval` are
both divided by `SPEEDUP`, and so is the suite's own `sleep`.

Scaling *both* kinds of timer, and the sleeps with them, is the part that matters. The plugin's 1 s
poll, its 100 ms observer debounce, its 300 ms click delay and its 2 s caption flash stay in the
same proportion to each other and to what the test waits for, so what is being exercised does not
change. Scaling only the interval would have left a 300 ms `setTimeout` outlasting a sleep that used
to cover it — a different test rather than a faster one. The sleeps are still written at the real
durations the plugin works in, so each call still reads as "one tick" or "two ticks".

`propagate-apply.test.js` keeps one deliberate 4 s wait: it is the `UNDO_ARM_MS` window itself,
which is the thing under test rather than a delay to be got around.

## How it works

The plugins are ES5 IIFEs with no exports, so there is nothing to `require`. Instead
`harness.js` (or `npt-harness.js`, whose DOM is real enough for a plugin that builds a
whole dialog — it serves every plugin here, taking the source path and plugin id as
arguments, with `dialog(body, prefix)` reading any one's markup) evaluates the plugin inside a `vm` context holding a hand-rolled browser
— `window`, `document`, `fetch`, `sessionStorage`, `MutationObserver` — and the tests
drive it the way a browser would.

**Two harnesses, deliberately, not by drift.** `harness.js` fakes just enough browser for
a plugin that injects a button (`merge-logic`, `logging`, `staging`, `coop`);
`npt-harness.js` builds a DOM real enough to append, walk and read back a whole dialog,
and drives runs by posting a `runPluginTask` mutation rather than by simulating a click.
Merging them would mean rewriting four suites onto a differently-shaped API to delete
about 150 lines of fake DOM — the cheaper harness is what keeps those four short.

Both are driven the same way: by answering the plugin's GraphQL requests and by calling
the event handlers it attaches. Assertions are a `check(name, condition)` helper; there
is no test framework.

Each suite runs in its own process, because the plugin installs global state (it wraps
`window.fetch` and registers intervals) that must not leak between suites.

`npt-harness.js`'s fake elements carry `previousSibling` alongside the `nextSibling` they already
had - added for the deterministic-ordering tests below, which walk backward from an anchor button
the same way a real DOM's sibling chain would. Missing beforehand, silently: every ordering check
that landed with it passed against the unfixed plugin too, since the priority scan's backward walk
never advanced past the anchor at all.

Three more of its fixtures grew with the scoped review dialogs: a dispatched `click()` carries
`currentTarget`/`target` as a real browser does (a handler reading its own button off the event
would otherwise crash only here), `querySelectorAll` honours the last segment of a descendant
selector (`#performer-page .details-edit` — the ancestor half is proved against a real DOM in
`placement.test.js` instead), and every context is seeded with a `window.__GTTx__`, the one global
these plugins reserve, so a suite can replace the coop object wholesale before the plugin has
created it. A test that does replace it must write **both** names — `window.__GTTx__.StashPluginCoop`
and the `window.StashPluginCoop` alias — or the plugin reads the namespaced one and never sees it.

### `NormalizeParentTags` settings are one string now

Its harness exports **`autoModes({ scenes: 'prune' })`**, which builds the `a1AutoModes` value the
plugin has read since its 4.0.0 (`PERFORMERS=OFF, ..., SCENES=PRUNE, ...`), and **`storedModes(...)`**,
which builds the `localStorage` entry the run dialog uses to remember a selection. A suite naming
any `aN` key of its own gets **no default** merged over it — that is either the new string or the
pre-4.0.0 booleans it replaced, and defaulting over the second would hide the migration such a case
exists to exercise.

There is one writing task (`TASK_RUN`) and a settings one (`TASK_MODES`); which direction a type is
planned in comes from the settings, not from which task was started, so a roll-up case is a settings
case.

### Checking that a test actually tests something

`SRC` points the harness at a different copy of the plugin, which is how these suites
were validated in the first place — every regression test was confirmed to fail against
the version before its fix:

```
SRC=/tmp/old-version.js node tests/merge-logic.test.js
```

### A plugin's display name is fixture data

Several suites build the settings-page or Tasks-page markup Stash would render, which means
writing the plugin's name into an `h3` and expecting the plugin to find itself by it
(`normalize-auto`, `normalize-tasks`, `placement`, `propagate-base`, `merge-task`). Those
literals carry a prefix as of `NormalizeParentTags` 2.0.0 / `MergePerformerTagsToScenes` 2.0.0 /
`PropagateTagsAndPerformers` 1.0.0 — the ASCII `GTTx ` then, and `ᝯㄝₓ ` since those plugins'
3.0.0 / 3.0.0 / 2.0.0 and `CustomFieldsBulkEditor` 2.0.0. They move with any rename, along with the
dialog-heading assertions — they are a copy of the `.yml`'s `name:`, and nothing checks the two
against each other. A stale one fails loudly rather than silently, since a plugin that cannot find
its own settings group does nothing at all.

**Only `cfbe` fails on a stale *manifest* name, though.** The three older plugins reach their own
settings group through the `plugin-<id>-<key>` ids Stash builds from the plugin id, and match the
heading only as a fallback, so a `.yml` renamed without its `.js` leaves them looking normal while
`CustomFieldsBulkEditor` — whose only route in is the heading — silently decorates nothing. That is
what the ᝯㄝₓ rename hit live, and it is the shape of failure to expect from any future one.

## What they do not cover

These are simulations of Stash, not Stash. They pin down the plugin's own logic and
its assumptions about Stash's markup and component props — they cannot tell you those
assumptions are still true after a Stash upgrade. The staging suite is the most
exposed, since it models `useTagsEdit`'s behaviour rather than calling it. A passing
run is not a substitute for clicking the buttons once in a real instance.
